> 版本：v0.2（技术详设，2026-11 补充 P1 体量闭环）
> 前置文档：[项目计划书](PROJECT_PLAN.md)
> 开源选型依据：[开源项目适配对比](OPEN_SOURCE_COMPARISON.md)
> 专项复盘：[布达拉宫建模复盘](POTALA_CASE_STUDY.md)

## 1. 适用范围与验收口径

本方案覆盖三类对象：

| 对象 | 典型内容 | 首期目标 |
| --- | --- | --- |
| 建筑/场景 | 宫殿、寺院、街区、室内空间 | 主视图高一致，其他视角合理，构件级可编辑 |
| 产品/静态道具 | 家具、设备、商品 | 轮廓与比例准确，部件与材质可编辑 |
| 植物/自然环境 | 树、灌木、地形、水面 | 形态相似、可参数调整、支持实例化与 LOD |

**“主视图高一致”的验收定义**：

1. 主参考图机位下，主要外轮廓与关键分界线对齐；
2. 主要体量的高度、宽度比例与参考图一致（相对误差目标 ≤ 3%，人工确认）；
3. 主体颜色分区与参考图一致（红/白/深色带等分区不得错位）；
4. 其他视角的结构合理，不出现明显纸片感、悬空体块或穿插；
5. 未观测区域在 `scene.json` 中标为推断，不伪装成事实。

不承诺测绘级精度，不承诺单图恢复被遮挡结构。

## 2. 能力边界

- 单图只能恢复可见结构；背面、进深、内部布局属于推断。
- 无尺度参考时使用类别先验，尺寸字段必须标记 `estimated: true`。
- 摄影测量得到的融合网格默认是“代理”，不直接视为可编辑工程模型。
- 复杂地标不接受“一键生成即可发布”的交付方式，必须经过灰模确认。
- 生成式单物体模型（TRELLIS/TripoSR 等）只用于近景独立道具，不用于整栋地标。

## 3. 总体架构

```text
输入层    照片 / 地名 / EXIF / 参考资料
             ↓
勘察层    质量检查、多图分组、覆盖评估、地点确认、尺度来源、隐私授权
             ↓
证据层    VLM 结构化理解
          Grounding DINO 检测 + SAM 2 分割
          Depth Anything V2 深度先验
          COLMAP 相机与稀疏几何（多图时）
          OSM/DEM/参考资料（地点可确认时）
             ↓
契约层    scene.json（唯一真源）+ survey.json
             ↓
生成层    Blender 执行器
          ├─ Architecture Builder
          ├─ Product Builder
          ├─ Vegetation Builder
          └─ Terrain Builder
             ↓
验证层    灰模门禁 → 主视图对照 → 多视角检查 → 降级验收
             ↓
交付层    BLEND 母版 / GLB LOD / 预览图 / 报告
```

### 3.1 分层职责

| 层 | 允许做的事情 | 不允许做的事情 |
| --- | --- | --- |
| 勘察层 | 评估、提问、给出补拍建议 | 在证据不足时直接生成“看似完整”的场景 |
| 证据层 | 输出观测、置信度、来源 | 直接决定最终几何参数 |
| 契约层 | 记录事实、推断与决策 | 保存无法追溯的临时状态 |
| 生成层 | 按契约确定性构建 | 自行修改契约或猜测未记录的参数 |
| 验证层 | 阻断不合格结果 | 用装饰细节掩盖体量错误 |

## 4. 输入处理与勘察

### 4.1 多图分组

多图分为三种关系，必须先分类再处理：

| 关系 | 判定 | 处理 |
| --- | --- | --- |
| 同一场景多视角 | 特征/几何一致，光照连续 | 进入 COLMAP 联合重建 |
| 同一物体不同角度 | 背景不同但主体一致 | 单物体多视角，主体分割后匹配 |
| 无关参考图 | 主体或场景不一致 | 不参与几何，仅作风格/材质参考 |

首期使用 COLMAP 的匹配结果做客观判定，视觉相似度只作辅助，不作为唯一依据。

### 4.2 覆盖评估

- 记录每张照片的估计方位扇区与俯仰范围；
- 计算重叠比例与基线长度，判断是否具备视差；
- 输出缺失方向与具体补拍指令，而不是笼统提示“多拍几张”；
- 覆盖不足时，建筑类默认降级为“主视图优先”的重建模式。

### 4.3 尺度来源

按可信度排序：

1. 用户提供的实测尺寸或图纸；
2. EXIF 焦距 + 已知距离控制点；
3. 地理数据（DEM/建筑轮廓/楼层数）；
4. 类别先验（门窗高度、层高、桌椅高度）。

任何尺度都必须写入 `scene.json` 的 `dimensions.estimated` 与 `assumptions`。

### 4.4 隐私

- 默认本地处理；上传云端视觉模型前记录当次授权到 `inputs.allowExternalUpload` 与 `sources[].externalUpload`；
- EXIF GPS 只写入受控字段，不进入公开报告与日志；
- 公开仓库不提交原始照片。

## 5. 证据层

### 5.1 图像观测

观测是“某张图片上的一次检测/分割结果”，不是场景实体。统一记录：

```json
{
  "observationId": "obs_0001",
  "photoId": "photo_front",
  "label": "red_palace_facade",
  "prompt": "red palace facade",
  "bbox": [x0, y0, x1, y1],
  "maskRef": "assets/masks/obs_0001.png",
  "detector": { "model": "grounding-dino", "score": 0.71, "threshold": 0.3 },
  "segmenter": { "model": "sam2", "score": 0.88 },
  "depth": { "model": "depth-anything-v2-small", "kind": "relative", "stats": {} },

  "observedColorSrgb": "#A32A22",
  "sourceModelsFixed": true
}
```

要求：

- 检测分数与分割分数分开保存，不合并成一个“置信度”；
- 保存模型、权重版本、阈值与预处理参数，保证可复现；
- mask 作为独立资产，记录 sha256。

### 5.2 观测与实体

- 单图场景：观测可直接映射为实体，但保留 `observationIds` 回溯。
- 多图场景：先由 COLMAP 稀疏点把各图 mask 反投影到三维，再按空间一致性与标签投票合并为实体。
- 跨独立照片不做外观相似度直接合并；重复窗户、重复立面外观极易误配，必须结合三维位置与行列索引。

### 5.3 颜色、材质与反照率

照片颜色 = 反照率 × 光照 × 曝光 × 反射，不等于材质参数。

- 保存 `observedColorSrgb` 作为观测；
- 反照率估计写入材质并标记 `inferred`，记录估计方法；
- PBR 粗糙度/金属度只允许来自明确模型或人工确认，不允许凭颜色猜测后当作事实；
- 同一立面的不同色阶（年代差异、重刷痕迹）应保留为多个材质，不要压成单一色号。

### 5.4 多视角几何

默认管线：

```text
照片质量过滤
   → COLMAP 特征提取与匹配
   → 相机位姿与稀疏点云
   → 尺度对齐（控制点/实测/地理数据）
   → OpenMVS 或 Meshroom 稠密重建与纹理化（可选）
   → Blender 清理、拆分、重拓扑或作为代理
```

用途划分：

| 输出 | 用途 |
| --- | --- |
| 相机参数 | 驱动“主视图对齐”校验与参考渲染 |
| 稀疏点云 | 跨图 mask 反投影、实体关联、粗略尺度 |
| 稠密网格 | 近景复杂几何的代理或纹理来源 |
| 深度图 | 遮挡关系参考，不作为米制尺寸 |

VGGT 仅作为试验性前端：输出相机/深度/点图并导出 COLMAP 格式，后续仍走 COLMAP/OpenMVS 验证。

### 5.5 证据不足时的降级

| 情况 | 降级策略 |
| --- | --- |
| 单图 + 未知地点 | 类别先验 + 主视图轮廓约束，标注 `style_reference` |
| 单图 + 已知地点 | 引入 OSM/DEM/参考资料，背面按结构与资料补全 |
| 多图覆盖不足 | 不承诺完整几何，只做可见区域与原图对齐 |
| 反光/透明/动态物体 | 不进入高精度几何，改用参数化或材质近似 |

## 6. 场景契约

`scene.json`（JSON Schema `schemas/scene.schema.json`）是唯一真源。当前 Schema 已覆盖元素、来源、相机、资产、环境、母版、发布档与五道验收关卡。

### 6.1 现有字段的用法

| 字段 | 用途 |
| --- | --- |
| `elements[].reconstruction.method` | 声明 photogrammetry / ai_3d / parametric / geodata / template / procedural |
| `elements[].reconstruction.generator` | 固定生成器 URI、入口与参数，保证可重建 |
| `elements[].confidence` | 该实体的综合置信度 |
| `elements[].assumptions` | 推断项，必须逐条可读 |
| `elements[].confirmation` | 用户确认状态与时间 |
| `elements[].locked` | 已验收区域锁，禁止自动覆盖 |
| `elements[].qualityTarget` | master / high / medium / low |
| `acceptance` | survey / layout / keyAreas / photoComparison / lod 五道门禁 |

### 6.2 建议新增（v1.1，需单独评审）

为支撑“观测可追溯”与“保真度分级”，建议新增：

| 字段 | 说明 |
| --- | --- |
| `observations[]` | 单图观测记录（bbox/mask/模型/阈值） |
| `relations[]` | 实体关系（supports / above / contains / adjacent），附 `basis` |
| `elements[].fidelity` | `measured` / `inferred` / `concept`，明确交付性质 |
| `elements[].geometryConstraints` | 主视图轮廓、轴线、对称、重复阵列等约束 |
| `cameras[].solvedFrom` | 相机来源（EXIF / COLMAP / 手动），用于对齐校验 |

Schema 变更必须：更新版本号、提供迁移说明、同步示例、通过负向测试。

## 7. Blender 生成层

### 7.1 执行方式

- **Headless Python**：正式构建、批量生成、自动化测试；保证确定性。
- **Blender MCP**：交互式查看与局部修改，例如选中某面墙移动 0.5 m。
- 两者共用同一套 Builder，禁止维护两份建模逻辑。

### 7.2 Builder 接口

```python
build(scene_document, element_id) -> BlenderObjectTree
```

约束：

- 输入只来自 `scene.json` 与受控资产，不允许读取未记录的外部状态；
- 相同输入必须产生相同几何（数值确定性）；
- 输出必须保留语义命名与父子关系，如 `pot_red_palace / facade / window_row_03 / window_07`；
- 失败必须返回阶段、元素 ID 与原因，不允许只抛通用异常。

### 7.3 场景装配

- 元素按 `layer`（near/mid/far/dynamic）与 `qualityTarget` 装配；
- 重复构件使用共享网格 + Array/Geometry Nodes，不复制顶点；
- 保留“编辑版”（完整对象树）与“导出优化版”（按材质合并）两份，导出优化不得覆盖母版结构。

### 7.4 建筑 Builder

按四步推进，每步独立验收：

```text
① 体量与轮廓（无窗、无贴图）
   → ② 主要分区（红/白/台基/屋顶群）
   → ③ 立面细节（窗、带、柱、檐）
   → ④ 材质、纹理、灯光
```

关键规则：

1. **禁止导出前整体拉伸**凑照片宽高比。比例应在相机与体量参数中求解并记录。
2. **收分与退台参数化**：墙体收分、退台步长作为参数；相邻体块避免共面，防止远景闪烁。
3. **窗户是构件而非贴片**：窗洞、窗框、窗棂、窗台分层；重复阵列用实例，不用逐窗独立网格。
4. **按区域独立阵列**：不同立面/楼层允许不同窗距、窗高与排布，禁止全楼套同一参数。
5. **屋顶类型显式**：可见坡面先建，未知背面标为假设；屋顶群高差、屋脊与檐口必须独立可控。
6. **墙带分层**：底层墙、饰面、边玛带、白线独立对象，避免一条深色带“画”在墙上。

#### 7.4.1 参数化体量的落地方式（P1 已实现）

体量参数写在 `scene.json` 的 `elements[].reconstruction.generator.parameters`，由 `pipeline/massing_params.py` 展开后交给 `generators/architecture/potala_massing.py` 构建，禁止在生成器里写死坐标。

| 参数结构 | 语义 |
| --- | --- |
| `boxes[]` | 轴对齐体块：`name/x0/x1/y0/y1/z0/z1`，可带 `repeat`（沿轴重复阵列）与 `slopeZPerX`（坡面剪切，`z_actual(x) = z0 + slopeZPerX*(x - xRef)`） |
| `prisms[]` | 坡屋顶棱柱：底/顶轮廓点串 + 高度，用于金顶、斜檐、坡屋面 |
| `material` | 元素级材质键（如 `clay`、`roof_gold`、`wall_red`），缺省 `clay` |
| 子体块 `scope` | 标 `complex` 的体块只在 `complex` 地标参与配准投影，避免外围延伸墙虚增主体宽度 |

生成与校验的边界：

- 生成器只读契约与受控资产，遇到缺相机、缺材质直接 `[FAIL]` 退出，不静默降级；
- 重复构件按参数展开，不在脚本里复制坐标；
- 渲染为固定机位（`CAMERA_ID`）与固定采样（Cycles CPU 40），保证回归可比。

### 7.5 产品/道具 Builder

- 主体几何优先参数化（箱体、回转体、圆角、倒角）；
- 复杂曲面部件的网格由 TRELLIS/TripoSR 生成后导入，作为 `ai_3d` 资产；
- 生成资产必须重新命名、缩放归一、材质对齐，不能直接作为最终对象；
- 保留“参数化部分 + 网格部分”的混合结构，避免整件都变成不可编辑网格。

### 7.6 植被与地形 Builder

- 单株植物：参数化（高度、冠幅、分枝角、叶片密度、季节色）或 Infinigen 生成器；
- 群落：Geometry Nodes 按密度、坡度、水线、道路避让做散布；
- 地形：DEM/地理数据优先；无数据时用轮廓约束的高度场；
- 水面、天空、雾：以参数与动态效果描述，不烘焙成静态网格；
- LOD 只降低实例密度与纹理分辨率，不改变母版分布。

### 7.7 材质与光照

- 材质绑定 `observedColorSrgb` + 反照率估计 + 纹理来源；
- 光照按时间、地点、照片阴影方向联合估计，记录 `estimated`；
- 参考渲染必须使用与主照片相近的焦距、机位与光照，用于对照验收。

### 7.8 导出

| 产物 | 内容 |
| --- | --- |
| `master.blend` | 完整对象树、参数、材质、相机、灯光 |
| `master.glb` | 高精度归档版，保留部件命名 |
| `lod0~lod3.glb` | 按发布档减面、纹理压缩、实例简化 |
| `previews/` | 主视图、三分之四、低机位、关键区域特写 |
| `reports/` | 勘察、灰模、对照、降级报告 |

## 8. 质量门禁与验证

### 8.1 五道门禁

| 门禁 | 判定内容 | 阻断条件 |
| --- | --- | --- |
| survey | 输入质量、地点、覆盖、隐私、尺度来源 | 关键信息缺失或未授权上传 |
| layout | 体量、朝向、比例、相机 | 主视图轮廓未对齐 |
| keyAreas | 用户指定重点区域 | 重点区域明显错误 |
| photoComparison | 主视图与原图对照 | 形/位/色/缺四项均有未处理问题 |
| lod | 各发布档 | 降级导致主体结构破坏 |

上表是人工确认型门禁；**结构性漏项**另由覆盖门禁自动判定，避免“照片里看得到、场景里没建”靠人眼发现：

- 输入：勘察 `regions[]`（照片区域 → 可见结构类别）与场景元素的 `structureClasses` / `photoRegions`。
- 命令：`python3 pipeline/coverage_check.py --survey <survey.json> --scene <scene.json>`，结果写入场景目录 `derived/coverage-report.json`。
- 判定：任一区域声明的结构类别，若没有任何元素“同时”声明该类别并引用该区域，即失败；`waiver.reason` 只能显式豁免。元素引用不存在的区域同样失败；勘察未定义 `regions` 时默认失败，防止静默放行。
- 粒度：按“区域 × 结构类别”判定存在性，不比较数量与位置；要卡住局部缺失，应把区域拆成更细的层带，而不是只框一整块。
- 配准：`python3 pipeline/registration_check.py --survey <survey.json> --scene <scene.json>` 用相机把场景几何投影到 `photoLandmarks` 包围盒；中心偏移、宽/高相对误差超过 tolerance（缺省 5%）或 IoU < 0.7 即失败，并输出 `derived/registration-overlay.svg` 供人眼复核。compare.html 的透明度叠加只是并排对照，不能当作配准证据。
- 相机参数化：相机一律用“目标点 + 环绕方位/俯仰/距离 + fov”描述（`fit_camera.py` 以 `--anchor-x/--anchor-y` 固定目标点水平位置，写回时在 `orbit` 字段留痕）。相机水平位置只能由方位角与距离推出，不能独立横移——否则求解器会用平移去吸收几何比例误差，把正视图拟合成斜视。正视图必须加 `--lock-azimuth` 把方位锁死。
- 尺度约束：两张无 EXIF/GPS、无同名点的照片无法唯一确定绝对尺度（距离与焦距共模）。因此配准门禁只保证“在给定相机族内几何能否对齐”，绝对尺寸必须另有尺度锚（真实尺寸或 EXIF/GPS），否则残差只能说明比例问题，不能反推真实米制尺寸。场景根级用 `scaleAnchor`（`source/totalWidth/totalHeight/unit/note`）把外部尺度写进契约，缺省的均匀缩放对成像不可观测。
- 地标口径 `scope`：`photoLandmarks[].scope` 取 `palace_proper`（缺省，只含宫殿主体）或 `complex`（含外围延伸白墙等完整剪影）。生成参数里标 `scope: "complex"` 的子体块（如 `white_base_outer_w/e`）只在 `complex` 地标参与投影，否则主体宽度会被外围延伸段虚增。
- 流程约束：新增/删除场景元素或修改勘察区域后，必须重新运行覆盖门禁，报告与场景同版本归档。

### 8.2 P1 体量基线（布达拉宫，2026-11）

可执行链路与产物：

```bash
python3 pipeline/coverage_check.py    --survey examples/potala-survey.json --scene scenes/potala-palace-lhasa/scene.json
python3 pipeline/fit_camera.py        --survey examples/potala-survey.json --scene scenes/potala-palace-lhasa/scene.json \
  --photo photo_front --camera camera_front --lock-azimuth --elevation-limit 2 --write
python3 pipeline/registration_check.py --survey examples/potala-survey.json --scene scenes/potala-palace-lhasa/scene.json
```

| 门禁 | 当前结果 | 说明 |
| --- | --- | --- |
| survey | 通过 | 尺度锚 `scaleAnchor` 400m×117m 已记录来源 |
| 结构覆盖 | 15/15 | 区域 × 结构类别全部有元素承接 |
| layout（主视图） | 2/2 通过 | `building_main` IoU 0.81、`red_palace` IoU 0.90 |
| layout（正视图） | 0/2 通过 | `front_building` 高度 +12.2%、`front_red_palace` 宽度 −13.7% / IoU 0.55 |

未通过项的根因与处置方向：

- **正视整体高度偏高**：模型东侧白墙脚随地形下探到约 −32m，照片里白墙下沿近似水平，导致投影可见高度虚增。属于地形与墙脚建模口径问题，不应靠调整地标包围盒掩盖。
- **红宫偏窄**：正视图折算需约 71~72m，而主视图在 62m 时宽度误差已 +5.9%。两视角方向相反，说明红宫进深/前脸退后量也参与了宽度投影，需联合主视图独立量测后再定，不能单向加宽。
- **地标置信度**：`front_red_palace` 下沿由 0.440 修正为 0.476（旧值把红宫竖向压扁约 26px，曾造成“两视角照片自相矛盾”的误判）。地标 bbox 必须写明每条边的判读依据与歧义点，否则残差无法归因。

### 8.3 轮廓对齐指标

在渲染图中提取主体轮廓，与原图分割 mask 比较：

- 轮廓 IoU（目标 ≥ 0.85，人工确认后放宽）；
- 关键分界线（红白分区、台基顶线、屋顶檐口）的像素距离；
- 主要高度比例误差（≤ 3%）；
- 关键轴线与对称性检查。

指标只用于定位问题，不替代人工确认。

### 8.4 回归验证

- 每次构建生成固定机位渲染，与基线图做差异对比；
- 结构参数变更必须附差异说明；
- 已锁定区域（`locked: true`）不得自动改变。

### 8.5 失败分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| blocking | 体量/相机错误，后续无意义 | 停止，回到 layout |
| major | 局部结构错误 | 修复后重跑对应元素 |
| minor | 材质/细节偏差 | 记录并可延后 |

## 9. 布达拉宫专项

详见[布达拉宫建模复盘](POTALA_CASE_STUDY.md)。核心结论：

- 旧模型是人工固定参数近似，且用 `XS = 2.75` 整体拉宽凑比例；
- 窗户为贴片面板，屋顶与墙带使用通用规则，导出前按材质合并；
- 新流程必须“轮廓优先 → 白模确认 → 分区 → 立面 → 材质”，并以主视图高一致为验收口径。

## 10. 性能、确定性与缓存

- 照片、mask、点云、重建结果按内容哈希缓存，避免重复计算；
- 云端调用做结果缓存与重试上限，失败不静默降级为猜测；
- 大型场景按元素并行构建，单元素失败不影响其他元素产出；
- 导出前统计面数、纹理体积与对象数，写入报告。

## 11. 安全、许可与合规

- Blender 执行器只接受白名单操作与受控脚本，不执行模型自由生成的 Python；
- 外部服务适配器统一管理密钥，从环境变量读取；
- 每次外部调用记录服务名、模型版本、授权状态与数据范围；
- 资产与数据的许可分别记录，OSM 数据需 ODbL 署名；
- 未确认许可的网络图片不得作为贴图。

## 13. 已知风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 单图推断被当成事实 | 交付失真且难以追责 | `fidelity` 与 `assumptions` 强制记录 |
| 多图覆盖不足 | 几何破洞、误匹配 | 前置覆盖评估 + 主视图优先降级 |
| 通用生成器套用复杂地标 | 越修越怪 | 体量先验收，细节后生成 |
| 云模型漂移 | 结果不可复现 | 固定模型版本与参数，结果缓存 |
| 许可误判 | 合规风险 | 默认链路只放许可清晰的项目 |
| 可编辑性被导出优化破坏 | 后续无法迭代 | 母版与导出优化版分离 |
